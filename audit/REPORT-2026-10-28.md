# تقرير فحص Fox5517 — النسخة الأصلية من غير إصلاحات

**التاريخ:** 2026-10-28. **النطاق المأذون:** تحميل/فك/استيراد واختبار فقط، أثناء تجهيز المستخدم للسورس والكلاينت.

## الخلاصة

**السورس بيتبني، والداتا بتتستورد، لكن النسخة ليست جاهزة للاعبين.**

- الـsolution الأصلية اتبنت في **Debug وRelease** على Windows 2022 باستخدام SDK **3.1.426**: **صفر errors و13 warning لكل configuration**.
- ملفات SQL الأربعة الأصلية اتنفذت بنجاح على **MariaDB 10.4.32** معزولة وفارغة، نفس رقم نسخة قاعدة البيانات الظاهرة عند المالك. ده لا يثبت تشغيل NHibernate أو الحفظ داخل اللعبة.
- **13 اختبار مكونات: 9 نجحوا و4 فشلوا.** الفشل يثبت **3 عيوب مكونات**، ومعهم **مشكلة ترميز مشروطة بغياب تهيئة code-page provider**.
- **كل الـ636 ملف upstream الموجودة في Git مطابقة للأصل بالبايت.** كل ملفات C# الـ615 والمشاريع الأربعة موجودة دون تعديل. النسخة الكاملة،810 ملفات، اتفكت واتحققت خارج Git قبل/بعد الاختبارات.
- مفيش إصلاح C# أو csproj أو config أو SQL، ولا تحديث حزم/framework، ولا تشغيل DLL الأصلية، ولا سيرفر عام أو اتصال كلاينت.

**CI الحمراء هنا نتيجة حقيقية، مش نجاح متخفي.** ما اتستخدمش `continue-on-error`، ومش هنتجاوز check مطلوب أو حماية فرع عشان ندمج النسخة الأصلية. دمج baseline لا يعني قبولها للإنتاج.

## 1. عيب مؤكد: استقبال header مجزأة يغلق اتصال TCP

**الأولوية: عالية قبل اختبار اللعب عبر الشبكة.**

- الاختبار `TCP-03-split-header` أرسل أول2 بايت فقط من header صحيحة طولها4 بايت، وانتظر معالجة هذه القطعة قبل إرسال الباقي.
- السلوك المرصود: **`PEER_EOF_AFTER_2_HEADER_BYTES`**؛ الطرف المرسل شاهد EOF، أي غلق جهة الاستقبال قبل اكتمال header.
- اختبارا التحكم نجحا: frame كاملة، وheader كاملة مع body مجزأة. بيانات الإطار كانت8 بايت اصطناعية صحيحة من ناحية طبقة framing، بلا تشفير أو أي حساب لاعب؛ ليست رسالة لعب فُحصت بواسطة handler.
- السبب المقروء في [AsynchronousServerSocket.cs](../vendor/FoxConquer5517/ServerCore/Networking/Sockets/AsynchronousServerSocket.cs#L259): عند السطر271 يشترط `EndReceive` أن يعيد header كلها دفعة واحدة؛ وإلا يبدأ `Disconnect` عند301. TCP لا يضمن وصول الحقل كاملًا في قراءة واحدة.
- كل من [GameSocket](../vendor/FoxConquer5517/MsgServer/Network/GameServer/GameSocket.cs) و[LoginSocket](../vendor/FoxConquer5517/LoginServer/Network/LoginServer/LoginSocket.cs) يرثان هذه القاعدة. الاختبار استدعى callbacks الأصلية عبر sockets على loopback فقط، **ولم يشغّل خادم اللعبة أو عميل5517**.

مهم للدقة: [المحاولة السابقة](https://github.com/ahmedzahran7710-prog/Red-Moon/actions/runs/40606569798) أعادت timeout في أداة التشخيص؛ لم نعتبره إثبات عيب. حسّنا **اختبارنا فقط** ليراقب EOF عند الطرف الآخر بدل الاعتماد وحده على اكتمال callback الخاص بالفصل، ثم حصلنا على الدليل أعلاه. لا تعديل للشبكة الأصلية.

## 2. عيب مؤكد: كتابة النص تتجاوز حدود الحقل داخل packet

**الأولوية: عالية لصحة بيانات البروتوكول.**

- `PACKET-02-field-boundary`: حقل بطول4 بايت عند offset4، وبعده marker اصطناعية قيمتها `A1B2C3D4` عند offset8.
- كتابة `ABCDEFGH` غيرت الحقل المجاور إلى **`48474645`**، أي بايتات `EFGH`، بدل الحفاظ عليه. اختبار نص قصير في نفس الحقل نجح.
- [PacketStructure.cs](../vendor/FoxConquer5517/ServerCore/Networking/Packets/PacketStructure.cs#L438)، السطر449، ينسخ `value.Length` من غير تقييده بـ`length` المعلن للحقل.
- ده **تلف بيانات حقل مجاور داخل buffer الاختبار**، وليس إثبات heap overflow أو استغلال عن بعد. لم نجرِّب حزمة هجومية على سيرفر أو بيانات لاعب.

## 3. عيب مؤكد: ثلاث فئات من نقاط بداية Arena غير قابلة للوصول

**الأولوية: متوسطة، وتمس نظامًا مطلوبًا من أول نسخة.**

- `ARENA-01-all-configured-tiers-reachable` استدعى الدالة الأصلية لكل قيم مستوى من نوعbyte، من0 إلى255.
- الخمس قيم المعرفة في الكود: `1500,2200,2700,3200,4000`؛ القيم التي رجعت فعليًا: **`3200,4000` فقط**.
- [ArenaEngine.cs](../vendor/FoxConquer5517/MsgServer/Structures/Qualifier/ArenaEngine.cs#L68) يفحص `<130` قبل فروع `else if` الأصغر، فيمنع الوصول إليها.
- فحص الحد129/130 أعاد3200/4000 كما في الأصل؛ ده توثيق سلوك، مش موافقة على التوازن الحالي.
- لم نختَر توزيعًا جديدًا للنقاط أو ranges، ولم نختبر Arena match كاملة أو ranking/rewards داخل اللعبة.

## 4. فشل مُعاد الإنتاج لكن مشروط: قراءة النص في process جديدة

- `ENCODING-01-fresh-process-ASCII-read`: قراءة عنوان اصطناعي من `MsgConnectEx.IPAddress` رمت **`NotSupportedException`**: لا بيانات للترميز1252.
- [PacketStructure.ReadString](../vendor/FoxConquer5517/ServerCore/Networking/Packets/PacketStructure.cs#L224) يستخدم `Encoding.GetEncoding(1252)`، وفي هذه العملية الجديدة لم يُسجَّل provider.
- **لا نستنتج أن كل تشغيل فعلي للسيرفر سيفشل:** تهيئة DB/اعتماديات أخرى أثناء startup قد تسجل provider، ولم تُختبر دورة startup الكاملة. لم نضف registration لتجاوز فشل الاختبار.
- كتابة بايتات رد الدخول نفسها نجحت؛ المشكلة المشروطة هنا في getter/قراءة الترميز، لا دليل على كسر الإصلاح المنشور لحجم packet.

## ما نجح فعلًا

- **6 اختبارات لأدوات الاستيراد**: تطابق الملفات، تضمين كل C#/csproj، توثيق المستبعدات، رفض مسارات غير آمنة، hashing، ومنع كتابة النسخة الكاملة إلى vendor. لا تُحسب هذه اختبارات لعب.
- التحقق من **810 ملفًا/278,410,351 بايت** للنسخة الكاملة، و636 ملفًا/3,865,911 بايت داخل Git. Git blobs نفسها طابقت SHA-256 الأصلي؛ لم يغير Git CRLF/BOM.
- Restore وبناء الـsolution الأصلية Debug وRelease، دون source patch أو framework override.
- **5 فحوص لبايتات `MsgConnectEx`**: النجاح52 بايت، الرفض12 بايت، type1055، offsets، وعنوانIP عندoffset20. تؤكد تنفيذ الجزء الذي قرأناه من إصلاحupstream، **لا اتصال العميل**.
- حقل نص قصير حافظ على marker، حد Arena129/130 وثّق السلوك، واختبارا TCP للـframe الكاملة والـbody المجزأة نجحا. مع فحوص الرد الخمسة يصبح الإجمالي9 نجاحات مكونات.
- استيراد `accountzf.sql` ثم `zf.sql`، ثم تشغيل `fix_cq_levexp.sql` و`cq_action_mod.sql` الأصليين داخل DB المؤقتة فقط. ملفات SQL نفسها لم تُعدل.
- الأعداد **بعد تنفيذ الملفات الأربعة**: جدولان فيaccountzf،76 فيzf، و10procedures. توجد2 حسابات،2 لاعبين،294item و139levexp؛ `cq_log` صار0 بعد السكربت الإضافي، رغم احتواء dump الأصلية على سجلات. القيم والأسماء وكلمات المرور غير منشورة في التقارير.

تعريف الـprocedures بنجاح ليس تشغيلًا لها. لا اختبار ORM/login/persistence أو صحة اقتصاد/محتوى SQL مكتمل.

## ملاحظات قراءة كود وبيانات — ليست تجارب لعب

### تجهيز Windows وOpenSSL يحتاج مراجعة قبل التشغيل

- [Utils.cs](../vendor/FoxConquer5517/ServerCore/Utils.cs#L8) يطلب المكتبة باسم`libssl`، بينما المرفق الأصلي اسمه`libeay32.dll`.
- قراءة PE headers فقط أثبتت أن الملفين الأصليين **x86 / machine0x14c**؛ اختبارنا managed اشتغلX64. لم ننفذ DLLs، ولم نُعد إنتاج `DllNotFoundException` أو `BadImageFormatException` أثناء handshake.
- لا تغيير اسم، لا استبدال binaries، ولا فرضx86 على المشاريع. نجاح الـbuild لا يحسم هذه المخاطرة.

### VIP teleport غير مكتمل في المسار المقروء

[الـhandler الأصلي](../vendor/FoxConquer5517/MsgServer/Network/GameServer/Handlers/1128-MsgVipUserHandle.cs#L50) يحتوي **26 call site** تكرر `ChangeMap(430,378,1002)` لوجهات متعددة، مع تعليقTODO. لا يصح إعلان تنقلVIP مكتمل لمجرد وجود handler؛ لم تُختبر الواجهة مع عميل.

### Trade والحفظ يحتاجان اختبارات تعطل وتزامن

[AcceptTrade](../vendor/FoxConquer5517/MsgServer/Structures/Trade.cs#L283) ينقل الأغراض ثم يخصم/يمنح العملات على خطوات، ولم نجد transaction تغطي العملية كلها في هذا المسار. [HibernateDataRow](../vendor/FoxConquer5517/DB/HibernateDataRow.cs#L27) يفتح معاملات لحفظ السجل الواحد. **مخاطرة تستحق فحصًا، وليست dupe أو فقد مال مثبتًا**؛ لم نجرِّب قطع DB وسط تبادل أو قبول متزامن.

## ما لم يُختبر والقرار العملي

لم يُختبر: تحميل العميل وسلامته أو login/end-to-end، startup مع native crypto، إنشاء/حفظ شخصية، قتال/EXP/loot، التجارة والاقتصاد تحت الفشل، Fan/Tower/Steeds/VIP/Arsenal، حرب/أحداث كاملة، خرائط بمعيار صحة محتوى، ضغط أو soak test طويل، وأمان الشبكة الشامل.
