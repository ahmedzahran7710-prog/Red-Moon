# الانتقال إلى هيكل RedMoon الجديد

هذه أداة **نقل إعدادات إلى مجلد جديد** على نفس الكمبيوتر وبنفس حساب Windows، من حزمة RedMoon المثبتة سابقًا إلى الحزمة الجديدة. ليست ترقية schema، وليست استيراد قاعدة أو وسيلة لنقل DPAPI بين أجهزة/حسابات مختلفة.

## قبل البدء

- احتفظ بالمجلد القديم كاملًا، خصوصًا `.local`، واعمل Export احتياطي للقاعدتين في HeidiSQL. لا ترفع النسخ الاحتياطية أو الخزنة.
- أوقف السيرفرين من **Stop-RedMoon.cmd في القديم** وانتظر `STOPPED`. لا تُغلق MySQL قبل إتمام الحفظ، ولا تستخدم taskkill لتجاوز انتظار الإيقاف.
- فك **الحزمة الكاملة المعتمدة** في مجلد آخر غير مثبت، ليس فوق القديم أو داخله أو داخل العميل. لا تستخدم ZIP التنظيم القديم ولا launcher-only hotfix.
- استخدم حساب Windows الذي جهز القديم. لا تعاود Setup لمجرد أن المجلد الجديد لا يحتوي `.local` بعد.

المثال الحالي:

```text
القديم: F:\AhmedZahran\RedMoon\RedMoon-Sorce
الجديد: F:\AhmedZahran\RedMoon\RedMoon-Source
العميل: F:\AhmedZahran\RedMoon\RedMoon-Client   ← يظل كما هو
```

هذه أسماء مقترحة للمجلد الجديد، وليست أمرًا بتغيير مسار القديم أو حذفه.

## نفّذ الانتقال

افتح **Migrate-RedMoon.cmd من الجديد** وأدخل مسار القديم عند الطلب. أو، لمستخدم PowerShell:

```powershell
.\setup\Migrate-RedMoon.ps1 -PreviousRoot 'F:\AhmedZahran\RedMoon\RedMoon-Sorce'
```

اترك السكربت يحدد Root من مكانه. لو مررته صراحة، يجب أن يكون المجلد **الجديد**. لا تشغّل النسخة القديمة أثناء النقل.

الأداة تتحقق قبل النسخ من:

- عدم تطابق/تداخل المجلدين، وعدم استخدام junctions/symlinks.
- وجود ملفات التشغيل الجديدة، وغياب `.local` أو إعدادات/مخرجات قديمة في الوجهة.
- marker تثبيت قديم مكتمل، وبروفايل مطابق لأسماء القواعد.
- إمكانية فتح الخزنة القديمة بـDPAPI، بدون توليد أو تغيير أي سر.
- توقف العمليات القديمة وإخلاء منافذ اللعبة/الأكونت/الربط. لا تقتل أي عملية، ولا توقف MySQL.
- سلامة ملفات الداتا؛ لا تنسخ scripts أو EXEs/DLLs مخبأة داخل مجلدات الداتا.

## ما يُنقل وما لا يُنقل

يُنسخ إلى الجديد فقط:

- `.local/runtime-secrets.dpapi` كما هي بالبايت، و`installed.json` بدون إعادة إنشاء التثبيت.
- `active-profile.json` مع الإبقاء على قيم الاتصال والعميل؛ تتحدث معلومة `SourcePath` إلى المجلد الجديد فقط.
- `Login.cfg` و`Shell.ini` بمحتواهما الحالي، تحت الاسمين الجديدين `RedMoon.AccountServer.ini` و`RedMoon.GameServer.ini`. لا تُستبدل تعديلاتك بdefaults مولدة.
- `GameMap.dat`، والملفات الموجودة داخل `ini` و`Maps` و`DMaps` و`Scene` عند وجودها. الملفات المناظرة في الحزمة الجديدة تستقبل محتوى القديم، مع rollback للوجهة عند فشل النسخ قبل نشر الحالة.

لا يُنسخ process record قديم، stop marker، logs، EXEs/DLLs قديمة، ملفات العميل، أو SQL. لا يوجد اتصال MySQL داخل سكربت الانتقال أصلًا. تظل الحسابات والشخصيات في نفس القواعد ونفس مستخدم التشغيل، ولا تتغير الـgrants أو كلمات المرور.

**مهم للملفات المخصصة:** الأداة تنقل المجلدات المعروفة فقط، ولا تستكشف أو تدمج تعديلات سورس أو مجلدات مخصصة أخرى تلقائيًا. كل غير المنقول يبقى محفوظًا في القديم. راجع أي تعديل خاص خارج الأماكن المذكورة قبل التفكير في الاستغناء عن القديم. لو لك قواعد firewall محددة بمسار EXE القديم، تحتاج مراجعة اختيارية صريحة للمسارات الجديدة؛ الانتقال لا يعدّل firewall تلقائيًا.

## بعد MIGRATION_READY

1. شغّل MySQL وHamachi، ثم **Start-RedMoon.cmd من الجديد**.
2. انتظر `SERVERS_READY`؛ هذه علامة بدء وربط الخادمين، وليست إثبات دخول العميل.
3. افتح العميل/اللودر اللذين نجحا عندك. لا تحتاج إعادة Install-ClientConfig لمجرد نقل السورس، لأن اسم السيرفر وعنوانه ومنافذه محفوظة.
4. راجع نفس الحساب والشخصية والعناصر والعملات والموقع، ثم جرّب خروجًا وحفظًا وإعادة تشغيل منظّمة.
5. احتفظ بالقديم وبنسخ قواعد البيانات حتى بعد التأكد، بدل الحذف الفوري.

التحقق المعزول يمكنه إثبات بناء/تشغيل وربط ومصادقة محاكاة وحماية إعدادات/سجلات اصطناعية. **لا يعوّض قبول عميلك وقواعدك الفعلية على جهازك، ولا اختبار كل أنظمة اللعب.**

## لو حصل رفض أو خطأ

- **الوجهة فيها حالة أو configs:** لا توافق على overwrite. استخدم فكًا جديدًا في مجلد جديد.
- **الخزنة غير مقروءة:** نفس حساب Windows ونفس الكمبيوتر أولًا. لا تشارك الخزنة ولا تعيّن passwords جديدة عشوائيًا.
- **سيرفر/منفذ مشغول:** أوقف النسخة القديمة بالطريقة الصحيحة، ولا تقتل عملية غير معروفة.
- **staging متروكة أو rollback غير مكتمل:** احتفظ بها وبالقديم وراجع رسالة الخطأ. لا تحذفها عشوائيًا أو تشغّل Setup بدلًا من مراجعتها.
- **فشل بدء الجديد:** احتفظ بالخطأ المنقح. استخدم Stop من الجديد حتى تُغلق كل عملياته، وتحقق من خلو منافذ السيرفر قبل الرجوع للقديم. لو Stop لا يستطيع إثبات الإغلاق، توقف للمراجعة؛ لا تبدأ نسخة ثانية فوقه.

**الرجوع:** بعد إيقاف الجديد بالكامل، ابدأ القديم من ملف Start الخاص به؛ لم تُغيّر الأداة ملفاته أو الـschema. النسختان تستخدمان نفس القواعد، لذلك الرجوع للكود القديم **ليس استرجاعًا تلقائيًا لحالة DB سابقة**؛ لا تستعد backup فوق بيانات أحدث دون مراجعة. لا تشغّل الاثنتين معًا، ولا تنقل scripts الجديدة فوق تثبيت القديم.
